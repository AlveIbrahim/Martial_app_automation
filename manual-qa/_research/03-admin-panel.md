# Martial Apps ADMIN PANEL - Manual QA Mapping Report

> **Provenance:** Generated by a research agent (Opus) on 2026-06-01, verified against the admin frontend source through late-May commits (May 26). Companion to `00-app-map.md` (the user frontend map).
>
> **Repo:** `ai-buddy/martial-apps/martial-apps-admin-frontend`
>
> **Why this exists:** The admin panel is a SEPARATE Next.js app (port 3002, app id `martial_dashboard`) used by platform staff, not club owners. Several things the user frontend treats as "gated" or "mysterious" (the code required to create a club, who can be a club owner, content tiers, support ticket answers) are actually controlled here. This report maps those hand-offs so user-app test "expected results" are correct and so testers do not hunt in the user app for things that only live in admin.

**Read-this-first staleness warning:** The repo's `CLAUDE.md` describes a generic Modernize/Flowbite admin template (products, sales, orders, inventory). That is the starter scaffold. The REAL, martial-apps-specific admin surface is a smaller set of wired pages. Trust the per-page status table below, not `CLAUDE.md`. Many template routes still exist but are hardcoded stubs (see Section 6).

## 1. WHAT THE ADMIN PANEL IS AND WHO USES IT

**Audience.** Platform admins / internal staff ONLY. It is NOT for club owners, senseis, secretaries, or members. Club operators do all their club management inside the USER frontend (`/dashboard/myClub/...`). This admin app governs the whole platform across all clubs.

**Hard access gate.** Two layers, both requiring the GLOBAL app role `app_admin`:
- `src/middleware.ts`: reads the `martial_dashboard_accessToken` cookie, verifies the JWT with `jose`, and if `payload.role !== 'app_admin'` redirects to `/auth/login?error=admin_required`. (If `JWT_SECRET` env is unset, middleware fails open and skips the role check; the client gate still applies.)
- `src/app/context/AuthContext.tsx`: on login AND on session restore, throws "Access denied" if `user.role !== 'app_admin'`.

So an `app_support` user or a normal `app_user` cannot log in here at all. There is exactly one effective role in this app: platform admin. (Public registration was deliberately disabled, commit `6f142f3`.)

**Tech.** Next.js 16 + React 19, cookie-based httpOnly auth (`martial_dashboard_accessToken` / refresh token, proactive refresh every 13 min, 30-min idle timeout), Axios to the same Go backend as the user app (`NEXT_PUBLIC_API_URL`, default `http://localhost:3000`), `socket.io-client` for live ticket updates, PostHog telemetry. Same backend, different app id header (`x-app-id: martial_dashboard`).

**Surfaced navigation (the real product).** From `Sidebaritems.ts`, the admin sidebar exposes exactly these, grouped:
- **Dashboard:** `/` (home overview)
- **Management:** `/clubs`, `/demo-clubs`, `/invite-user` (Club Owner Invitation), `/club-code-requests`
- **Security:** `/persons`, `/audit-logs` (Audit Trail), `/password-reset`
- **Library:** `/movement-types`, `/move-master-library`, `/belt-master-library`, `/warmup-videos`
- **Support:** `/help-management`, `/support-management` (Support Tickets)

Any other route folder in the repo (analytics, members, payments, orders, inventory, categories, permissions, settings, persons-detail, sample-page, moves-videos, icons, utilities) is NOT in the sidebar and is leftover template scaffolding (see Section 6).

## 3. WHERE ADMIN DRIVES USER-APP BEHAVIOR (the hand-offs)

### 3a. Club-creation invite CODES - this is the big one

The user frontend has a create-club wizard (`/dashboard/club/create`) but creating a club requires a valid CODE. That code originates HERE. There are two admin paths to issue one:

**Path A - Admin-initiated invite (`/invite-user`):**
1. Admin enters an email + recipient name, clicks "Send Invitation".
2. Backend generates a `ClubOwnerInvitation` with a `code`, an `expiresAt`, status `pending`, and emails it to the recipient.
3. The code (and expiry, resend count, status) is shown in the admin "Invitation History" table.
4. The invited person registers/logs into the USER app and uses that code in the create-club flow. When consumed, the invitation flips to `accepted` (`consumedBy` / `consumedAt` set).

**Path B - User-requested code, admin approves (`/club-code-requests`):**
1. A user in the USER app submits a "club creation request" (optional message). It appears in the admin `/club-code-requests` table as `pending`.
2. Admin clicks Approve (optional response note). Backend creates a `clubOwnerInvitation` and the approve response returns its `code` (admin sees `Invitation code: <code>` in the toast). The user is emailed/notified.
3. Admin can instead Reject (optional reason). Request flips to `approved` / `rejected` with responder recorded.

**Net for testers:** A regular user CANNOT self-serve a club into existence. To create a real club in the user app you need a code that an admin issued via Path A or Path B. There is no admin "create a club directly" button that works (the `/clubs` page create form is a stub - see Section 6).

### 3b. Demo clubs - the fast lane for QA (`/demo-clubs`)

This is the practical way to get a fully populated club + working logins WITHOUT the invite dance:
- "Auto-generate Demo Club" creates a club and a set of demo accounts (roles like `club_owner_primary`, plus others), all with password `Demo@1234`.
- "Seed Club" populates it with data (members, belts, etc.); status goes empty -> seeding -> seeded.
- "Reset Club" wipes it back to empty (requires confirm). "Sync Belts" reconciles club belts to master. "Hide" removes a demo club from the user app's discover list (visibility flag).
- Demo accounts (emails + the shared password) are copy-buttoned right on the card.

These demo accounts/clubs are real in the same backend, so logging into the USER app with a demo account gives a real owner/member experience on a real club.

### 3c. Global app role assignment (`/persons`)

Admin can set a user's GLOBAL app role to `app_user`, `app_support`, or `app_admin` (`rolesApi.assignRole`). This is the global role system the user-app map flagged as "defined in types but no UI consumes it" on the user side - the UI to SET it lives here in admin. Setting someone to `app_admin` is what lets them log into THIS admin app.
(Note: this is the platform-wide role, NOT per-club roles like sensei/secretary. Per-club roles are still assigned inside the user app's club members page.)

### 3d. Master content the user app reads (Library group)

Moves, movement types, master belts, and warmup videos created/edited here are the APP-LEVEL (`isAppLevel`) catalog the user app surfaces in its global library, belt reference, and warmup library. Two concrete tier hand-offs:
- **Warmup video `tier` (free/premium) is chosen in admin** (`/warmup-videos/add`). This is a per-CONTENT premium flag. (Per the user-app map, the user frontend does NOT actually gate warmups by tier today, so a premium-tagged warmup is still visible to free users in the user app - that mismatch is a user-app behavior, not an admin bug.)
- **Master belts** carry `numberOfClassesRequired` / `numberOfTeachingHoursRequired` and insight text set here, which feed progression/eligibility logic in the user app.

### 3e. Support tickets (`/support-management`)

A support ticket a user opens in the USER app (`/support`, `/support/[id]`) is ANSWERED here. Admin can: change status (submitted -> in_triage -> in_progress -> qa_testing -> resolved -> closed), change category (bug/suggestion/help), post admin replies (which the user sees back in their ticket thread), and ESCALATE to ClickUp (`/escalate`, sets `clickupTaskId`). Updates are live via socket on both ends.

### 3f. Help articles (`/help-management`)

The help center the user app reads (`/help`, `/help/[id]`) is authored here. Admin creates/edits categories + articles, sets `isPublished`. Unpublished articles should not appear in the user app's help center.

### 3g. Password reset (`/password-reset`)

Admin can force-reset any user's password and gets a temp password to hand over. Affects that user's ability to log into the USER app.

### 3h. Audit trail (`/audit-logs`, `/persons/[person] audit logs`)

Read-only record of platform events (logins, failed attempts, profile switches, etc.). Does not change user-app behavior, but lets admins observe it.

## 4. LIFECYCLE / WORKFLOWS THAT SPAN ADMIN + USER APP

1. **Club birth (request route):** User submits club-creation request in USER app -> admin sees it in `/club-code-requests` -> admin approves -> backend mints an invite code -> user enters code in USER app create-club wizard -> club exists, user is `club_owner_primary` -> user runs the club entirely inside the USER app from then on.
2. **Club birth (invite route):** Admin proactively invites a club owner in `/invite-user` -> recipient gets code by email -> recipient registers + redeems in USER app -> invitation flips to `accepted`.
3. **Demo/QA club:** Admin auto-generates + seeds a demo club in `/demo-clubs` -> hands demo logins (`Demo@1234`) to testers -> testers operate that real club in the USER app -> admin resets it afterward.
4. **Support loop:** User files a ticket in USER app `/support` -> ticket lands in admin `/support-management` -> admin replies / changes status / escalates to ClickUp -> user sees admin reply + status change live in their ticket thread.
5. **Content publishing:** Admin authors a help article or master move/belt/warmup -> publishes -> it appears in the USER app's help center / library / belt reference.
6. **Elevating a teammate to admin:** Admin opens `/persons`, sets a user's global role to `app_admin` -> that user can now log into the admin app.

## 5. WHAT IS ADMIN-ONLY vs WHAT OVERLAPS

**Admin-only (do NOT look for these in the user app):**
- Issuing/managing club-creation invite CODES (`/invite-user`).
- Approving/rejecting club-creation REQUESTS (`/club-code-requests`).
- Generating/seeding/resetting DEMO clubs and demo logins (`/demo-clubs`).
- Assigning GLOBAL app roles (app_admin/app_support/app_user) (`/persons`).
- Force password reset for arbitrary users (`/password-reset`).
- The platform AUDIT trail (`/audit-logs`).
- CRUD of MASTER library content - movement types, master moves/videos, master belts, warmup videos incl. their free/premium tier (`/movement-types`, `/move-master-library`, `/belt-master-library`, `/warmup-videos`).
- Answering/triaging support tickets + ClickUp escalation (`/support-management`).
- Authoring help categories/articles (`/help-management`).

**Overlaps (both apps touch the same data, but from opposite ends):**
- **Support tickets:** user opens (user app) / admin answers (admin app).
- **Help articles:** admin authors (admin) / user reads (user app).
- **Library content:** admin manages master catalog (admin) / user views + clubs customize per-club (user app).
- **Club-level membership/roles:** admin issues the owner code (admin), but ALL per-club member/role/fee management happens in the USER app's club members page, NOT here.
- **Subscription tier:** admin DISPLAYS a user's/club's tier (persons page) but does not set it; the user app also only displays tier. See Section 7.

These are stub/template leftovers. They are NOT relevant to user-app QA and should not be mistaken for real admin capability:

## 7. SUBSCRIPTION / TIER STATE - THE ANSWER TO "WHERE IS PREMIUM SET?"

**There is NO admin control to set a user's or club's account subscription tier.** Searched the entire admin `src`: `subscriptionTier` and `subscriptionStatus` appear ONLY as read-only display fields on the `/persons` page (and in the `Person` type). There is no "make this user premium" / "set club to paying" button, form, or endpoint in the admin app. The only tier-setting control that exists is the per-CONTENT `tier: free | premium` flag on individual warmup videos.

**Implication:** Account-level tier (free vs premium/paying for a user or club) is owned by the BACKEND, not togglable from this admin UI. To put a test account into the premium state you will need a backend/DB action (or a demo account that is seeded that way), not an admin-panel toggle. Do not promise testers an "admin sets premium" step - it does not exist in the UI.

## WHAT THIS MEANS FOR USER-APP TEST SCENARIOS

1. **Club creation is gated on an admin-issued code; bake that into setup.** A plain user cannot create a club unaided. Before any owner-side test, an admin must either (a) approve the user's request in `/club-code-requests` or (b) send an invite in `/invite-user`, then the user redeems the code in the user app's create-club wizard. Write the owner happy-path setup as "obtain a valid club-creation code from an admin first."
2. **For most QA, skip the code dance and use Demo Clubs.** The fastest way to get a real owner + populated club + working logins is admin `/demo-clubs` -> Auto-generate -> Seed -> hand testers the demo emails with password `Demo@1234`. Recommend this as the default seeding mechanism in the role-setup docs. Note testers must reset/regenerate between runs to get clean state.
3. **Tier-based test steps cannot say "admin sets premium."** The messaging free-tier gate (free users can only DM staff) and any other premium behavior must be set up via the BACKEND or a pre-seeded premium account, because no admin UI changes account tier. Replace any "have an admin upgrade the account" instruction with "use a pre-seeded premium/staff account."
4. **Premium-tagged warmups are still visible to free users - that is expected.** Admin tags a warmup `premium`, but the user app does not gate warmups by tier. So "free user sees a premium-labeled warmup" is NOT a bug. The tier label is admin-side metadata only.
5. **Global app role (app_admin/app_support/app_user) is set in admin, not the user app.** If a journey needs an `app_support` or `app_admin` user, that role is assigned in admin `/persons`. The user app has no UI to grant it. (This is separate from per-club roles like sensei/secretary, which ARE assigned in the user app's club members page.)
6. **Support-ticket "expected result" on the user side depends on an admin action.** When a test says "user files a ticket and gets a reply / sees status change," the reply and status transition come from an admin in `/support-management`. For a true end-to-end ticket test, script a tester-with-admin handoff: user submits in user app -> admin replies/changes status/escalates -> user sees it live. Do not expect the user app to auto-progress a ticket on its own.
7. **Help articles a tester sees in the user app are whatever admin published.** If a help-center test expects a specific article, an admin must have authored + published it in `/help-management`. Unpublished articles should be absent in the user app - testers can verify the publish gate by toggling `isPublished` admin-side.
8. **Library content (moves/belts/warmups) the user app shows is the admin master catalog.** Empty user-app library lists usually mean the admin master library was not seeded, not a user-app bug. Seed master content (or use a seeded demo club) before library/belt/progression tests.
9. **Do not look in the admin app for club rosters, per-club settings, calendars, attendance, analytics, or payments.** None of that is managed admin-side. Club operations live entirely in the USER app under `/dashboard/myClub/...`. The admin `/clubs`, `/members`, `/analytics`, `/payments` pages are dummies and prove nothing about real club state.
10. **Password-reset path:** if a tester is locked out, an admin can mint a temp password via `/password-reset`. Useful as an unblock step in account-setup docs.
