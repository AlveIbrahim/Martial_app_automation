## 1. APP OVERVIEW

**Product.** A mobile-first PWA for martial arts clubs (dojos). It serves two sides: (a) **club operators** (owners, senseis, secretaries) who run clubs — members, classes/calendar, exams, belts/curricula, attendance via QR, content library, analytics, broadcast notifications; and (b) **practitioners / families** — personal belt progress, class library, direct messaging, plus a **household** layer where a parent creates **child profiles** gated by **PIN** and **screen-time** limits.

**Platform.** Mobile-first PWA. Hand-rolled service worker at `public/sw.js` (registered by `src/components/pwa/ServiceWorkerRegister.tsx`); `public/manifest.json`; `next.config.js` explicitly does NOT use next-pwa. Install prompt + iOS "add to home screen" hint in `Header.tsx` (`useInstallPrompt`).

**Core tech (from `package.json`):**
- **Next.js 16.1.6** (App Router) + **React 19.2.4**
- **Redux Toolkit 1.9.7** + **RTK Query** — 23 API slices, all under `src/store/services/`
- **next-intl 4.8.3** — locales `en` + `fr`, selected via `NEXT_LOCALE` cookie (no URL locale prefix); config in `src/i18n/request.ts`
- **socket.io-client 4.8.3** — realtime DMs + cache invalidation
- **hls.js 1.6.16** (present but DORMANT — see §6/§8), **html5-qrcode 2.3.8** (QR scan, live), **next-cloudinary** (image/video URLs), **idb 8.0** (installed but UNUSED in `src/`)
- **FullCalendar 6.1.17**, **recharts 3.1** (analytics), **react-hook-form + zod**, **framer-motion**, **posthog-js** (analytics/telemetry), **react-toastify**, **tailwindcss v4**

**Auth + role resolution (high level):**
- **Cookie-based, httpOnly.** Tokens are NOT readable in JS. Cookie names: `martial_frontend_accessToken` / `martial_frontend_refreshToken` (`APP_ID = 'martial_frontend'`, `src/store/authConfig.ts`). `src/utils/auth.ts` token getters are deliberate no-ops.
- **Middleware (`src/middleware.ts`)** does COARSE auth only: allowlist of public/auth paths; any other path with no session cookie → redirect `/login`. **No role logic in middleware.** Authenticated users hitting `/`, `/login`, etc. are bounced to `/dashboard`.
- **Auth state** is hydrated client-side by `useAuthInitialize` (`src/hooks/useAuthInitialize.ts`) calling `getUserProfile` via the cookie, then `setAuthState` into Redux (`authSlice`). 401s anywhere trigger a single refresh attempt via `/auth/refresh-token` (`src/store/baseQuery.ts` + `src/lib/axios.ts`); failure → `/login?session=expired`.
- **Two separate role systems:**
  1. **Global app role** (`src/types/index.ts`): `Role = 'app_user' | 'app_support' | 'app_admin'` only. Read via `useUserRole()` → `isAdmin/isSupport/isUser`. There is **no admin/support UI** anywhere (zero routes consume `isAdmin`).
  2. **Per-club role** (`src/types/club.ts`, `UserClub.role`): `club_owner_primary | club_owner | admin | sensei | secretary | club_member | member`. Resolved in the authenticated layout into a simplified `userRole: 'owner' | 'member'` plus the raw `clubRole` string, exposed through `MyClubContext`. **"owner" = any of club_owner_primary/club_owner/admin/secretary/sensei** for the currently-viewed club.
- **Subscription tier** (`useSubscriptionTier`): `free | premium` (backend "paying" normalized to "premium"). Gates almost nothing today (see §3/§8).
- **Profile type** (`ProfileContext`): `parent | child`. Child mode is entered by PIN switch; restrictions are **navigation-only** (no page guards).

## 3. ROLES (verified against current code)

Role checks are **per-club** (resolved in `layout.tsx` from the URL `clubID`) — NOT global. The stale docs' "owner of Club A can access Club B's owner pages" claim is no longer accurate for the in-URL club. There is still **no centralized guard/HOC**; each page does inline `userRole`/`clubRole` checks, so enforcement quality varies page to page.

**`club_owner_primary`** — Full control of the in-URL club. Only role that can **transfer primary ownership** and add/revoke senseis (teachers page: `clubRole==='club_owner'||'club_owner_primary'`). Sees Settings tab, analytics, history, exams, promotions, scan-attendance, members mgmt.

**`club_owner`** (co-owner) — Same as primary except cannot transfer primary ownership. Maps to `userRole==='owner'`.

**`admin`** (club-level) — Maps to `userRole==='owner'` (treated as owner in layout). Blocked from teachers add/revoke (teachers page only allows the two owner roles). Otherwise owner-equivalent in current checks.

**`sensei`** — Maps to `userRole==='owner'` in the layout (this is the key change vs the stale RBAC doc, which mapped only owner/admin to "owner"). Consequences:
- "My Club" nav is VISIBLE to sensei (`isAnyClubOwner` includes `sensei`, layout line 269).
- Can access analytics? Analytics guard is `userRole==='member' || !isOwnerRole`, where `isOwnerRole = clubRole==='club_owner'||'club_owner_primary'` ONLY. So **sensei is BLOCKED from analytics** despite `userRole==='owner'`. Same pattern on `/history`.
- Allowed: calendar event creation, exams, promotions, grading, curricula, eligible-students, scan-attendance, library manage.
- Blocked: Settings tab (Header hides for `clubRole==='secretary'` but NOT sensei). The settings PAGE itself guards `userRole!=='owner'` → sensei passes that too. ⚠️ **MISMATCH: sensei can reach Club Settings** (`userRole==='owner'`), which the RBAC doc says should be owner/admin-only. Verify whether backend rejects sensei writes.

**`secretary`** — Maps to `userRole==='owner'` (layout treats as owner), so "My Club" nav shows. Explicit page-level blocks:
- Settings: Header hides tab for secretary; settings page also effectively blocks (analytics/scan check secretary).
- Analytics: blocked (`isOwnerRole` excludes secretary).
- Scan-attendance: explicitly blocked (`clubRole==='secretary'` → access-restricted).
- History: blocked (owner-role-only).
- Allowed: members mgmt (members page: `canManageMembers = club_owner||club_owner_primary||secretary`), curricula, eligible-students, belts edit, calendar events.
- ⚠️ MISMATCH risk: secretary is "owner" in `userRole`, so any page that gates ONLY on `userRole==='owner'` (not `clubRole`) lets secretary through. Testers should probe each owner-gated control as secretary.

**`club_member` / `member`** — `userRole==='member'`. View-only: club overview, calendar (view), members list (view), sites/rooms, progress, library (view), warmup. Cannot create events, manage members, see analytics/history/settings/teachers. My Club nav still appears IF they are owner/sensei/secretary in some OTHER club (nav is `isAnyClubOwner`, global across clubs).

**Parent profile** — Full nav. Owns household, children, PIN, screen-time. FUNCTIONAL.

**Child profile** — Entered via PIN switch (`ProfileContext`). Nav hides Messages, Support, My Club, Profile, Discover-clubs (`BottomNavigation`/`DesktopSidebar`: `currentProfileType==='child'`). Screen-time lock enforced server-side + localStorage cache (`screenTimeLock.ts`). ⚠️ **Restrictions are nav-only** — no page-level guard. A child profile can still deep-link to `/dashboard/messages`, `/support`, `/dashboard/household/child/[childId]`, club pages, etc. (confirmed: no `currentProfileType==='child'` guard in those page files). This is a genuine, current gap — testers should NOT file the deep-link reachability as a surprise; but DO verify backend rejects child-context writes.

**`app_admin` / `app_support` (global roles)** — Defined in types, `useUserRole` exposes `isAdmin`/`isSupport`, but **no route or component gates on them** and there is **no admin/support dashboard**. `/dashboard/admin/help` exists and `helpApi` is wired, but no `isAdmin` guard was found protecting it. Treat admin/support as **NOT-BUILT as a distinct experience**.

**`app_user`** — The effective role for everyone; all standard features work.

## 5. KEY END-TO-END FLOWS (per role)

**Club Owner (primary) — operator happy path:**
1. Register → verify email OTP → login.
2. `/dashboard/club/create` → complete `ClubCreationWizard` (basic info, discipline, colors) → club created.
3. Club overview `.../[clubID]` → generate QR / share link.
4. `.../site` → create a site → create a room (needed before scheduling).
5. `.../[clubID]/members` → approve a pending join request → assign a member the `sensei` role → create a fee tier.
6. `.../calendar` → create a class (pick room) → create a recurring class → create an exam (or via `.../exams`).
7. `.../belts` → define belt levels → `.../curricula` → assign curriculum to members.
8. `.../scan-attendance` (real device) → scan a member QR → attendance recorded → `.../history` shows it.
9. `.../exams/[examID]/grading` → grade candidates → `.../promotions` reflects results.
10. `.../analytics` → review membership/attendance/belts tabs.
11. `/dashboard` "Announcements" / messaging → broadcast a club notification.
12. `.../[clubID]/settings` → edit club, transfer primary ownership (only primary).

**Sensei:**
1. Login → My Club visible → open assigned club.
2. `.../calendar` create/edit a class or workshop; `.../exams` schedule + `.../grading`.

## 6. CROSS-CUTTING CONCERNS

**Realtime / socket (`src/hooks/useSocket.ts`, `GlobalSocketProvider.tsx`).** socket.io connects when authenticated (`query: { appId }`, websocket+polling). Live events: `dm:new_message`, `dm:message_edited`, `dm:message_deleted`, `dm:messages_read`, `dm:typing`/`dm:stop_typing`, plus `support:*` and notification events. `GlobalSocketProvider` invalidates RTK caches app-wide (Conversations, SupportTicket, TicketMessages, UserNotifications) so lists update live regardless of page. **To trigger:** two browsers/accounts in a shared club — send a DM from A, watch B's conversation list + open thread update without refresh; type in A to see B's typing indicator (auto-clears after 3s). Notifications: owner broadcasts → member's bell updates live.

**i18n (en/fr).** **French is essentially complete** — `messages/fr.json` has 3142 translated keys vs `en.json` 3145; only **3 keys missing** (`scanAttendance.cameraNotSupported`, `.cameraPermissionDenied`, `.cameraNotFound` → will fall back to key/English on camera errors). Only ~6% of values are identical to English, and those are cognates/proper nouns ("Martial Apps", "admin", "sensei", "actions"). Locale is driven by the `NEXT_LOCALE` cookie (set from user's `language`); switch via the in-app Language selector in Header. No `/en` or `/fr` URL prefix. **Test:** set French, sweep every page for layout breakage from longer French strings, and trigger a QR camera error in French to see the 3 untranslated fallbacks.

**Responsive + Tailwind breakpoints (v4).** Mobile-first. Actual usage: `sm:` 1223, `md:` 407, `lg:` 230, `xl:` 5, `2xl:` 0. The **primary layout switch is at `md:` (768px)**: below `md` the bottom nav shows and the desktop sidebar/main margin collapse (`pb-16 md:pb-0`, `md:ml-16`); messaging switches from full-screen single-pane (mobile) to split list+chat at `md` (`useMediaQuery('(min-width: 768px)')`). `sm:` (640px) does fine-grained padding/typography. `lg:` widens panels (e.g. messaging list `lg:w-96`). `xl:`/`2xl:` are negligible — don't expect distinct ultra-wide layouts. **Test matrix:** phone (<640), small tablet (~768 boundary — highest-risk transition), desktop (≥1024).

**PWA / offline.** Hand-rolled `public/sw.js` + `public/manifest.json`; registered via `ServiceWorkerRegister`. Install prompt with iOS hint. ⚠️ **`idb` is installed but UNUSED in `src/`** — there is **no IndexedDB offline data cache**. Screen-time lock uses `localStorage` only. Don't expect true offline data; test install/standalone + service-worker asset caching, plus update flow (`useServiceWorkerUpdate`). Pull-to-refresh exists (`usePullToRefresh`, `PullToRefreshIndicator`).

**QR camera.** `html5-qrcode` with `getUserMedia({ facingMode: 'environment' })` on `.../scan-attendance`. **Needs a real phone** (rear camera + HTTPS/localhost). Handles unsupported/denied/not-found camera states (those 3 strings are the untranslated-in-French ones).

**HLS video streaming.** `useHlsPlayer` is a complete hook (hls.js + native HLS + MP4 fallback + signed-URL 403 refresh) but **NOT imported anywhere** — DORMANT. Current playback (`components/library/MediaGallery.tsx`) is a plain `<video>` with Cloudinary URLs/posters. Test video as plain MP4; do not test adaptive-bitrate/HLS behavior.

**Image / file upload (Cloudinary).** `next-cloudinary` + `imageApi` (`useUploadImageMutation`, `useGetImageUrl` for signed URLs). Used for avatars, club logos/banners, library media (`MultiFileUpload`, `UnifiedMediaUpload`, `directVideoUpload.ts`). Test on real device for camera-capture upload.

**Telemetry.** PostHog (`posthog-js`) captures slow API calls (>1.5s), failures, nav clicks (`data-track`), club-context switches — not a tester feature but explains background network traffic.

**Genuinely needs a real phone:** QR scan-attendance, camera-based media capture/upload, PWA install (especially iOS add-to-home-screen), pull-to-refresh, swipe gestures (`useSwipeGesture`), and accurate touch-target/responsive checks at the 768px boundary.
